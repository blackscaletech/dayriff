# Architecture

A React view calls a same-origin Fastify server. Shared TypeScript interfaces define the small public API. Provider credentials and full planning state stay on the server.

## Boundaries

Qloo resolves artists and venues and retrieves a compact geographic shortlist. A shared cultural-quality policy excludes known generic chains and unsuitable businesses, then ranks positive cultural taxonomy alongside Qloo affinity. Initial planning can select stop identifiers and grounded notes only; submitted times, duration, starting point, and optional preferences remain server-owned. A feasible suggestion is checked before the model runs and can be accepted after bounded repair attempts or an unavailable optional model response, with enrichment and final validation under the same constraints. If artist-affinity discovery is empty or cannot form a feasible outing, at most two geographically scoped place-type searches can supply real local candidates; missing artist-affinity evidence remains explicit. Each follow-up first passes through one bounded semantic interpreter. The same interpretation call first returns place-policy facts grounded in exact clauses from the current user message. A pure reconciler distinguishes excluding a kind, withdrawing a requirement, allowing it again, and keeping a specific existing stop; it enforces replacement scope and leaves timing, counts and budget separate. Its validated immutable intent controls answer/change dispatch, total-stop bounds, positive taste scope, matching-kind minimum/maximum bounds, explicit withdrawals, real replacements, budget, arrival and walking changes. Operational search/check tools cannot reinterpret or overwrite that intent. A follow-up may call a bounded place-discovery tool: resolve actual Qloo category tags, retrieve artist-ranked places near the venue, or search locally and rerank matching IDs. Requested subtypes become server-validated matching-ID requirements, so a generic shop cannot stand in for a bookstore. Exploratory searches for alternatives add options without becoming new user requirements. A shared planning-window function derives the outing from the show date and time: default arrival is 30 minutes before the show, an explicitly supplied arrival replaces that default, and the exploration duration includes all visits and walks. Optional arrival clocks resolve to the most recent time before the show within a twelve-hour lead; incompatible values require clarification. The function retains signed minute offsets and calendar dates for previous-day starts and arrivals. Scheduling, listed opening hours, revision interpretation, chat answers, summaries, and restored versions use that same window; omitted arrival preferences remain absent. Routing estimates come from a routing provider when configured; approximation is labeled when that provider is absent.

A shared 120-second planning deadline (including provider fetches and pacing), provider timeouts, a 40-place session shortlist, at most four model calls and two discovery searches per revision, and bounded conversation history prevent unbounded work. Luna uses configurable medium reasoning by default. A compact intent call dispatches the turn; cached feasible goals are applied deterministically without a planning-model round. Broader count goals first use capacity-guided grounded discovery of shorter visits, derived from shared visit-duration defaults and the hard window; searches still count against the same two-search allowance and do not create tastes. Other unmet goals allow at most three operational model rounds. Initial planning retains its two-round limit. Each provider call has a finite token cap and timeout. Encrypted reasoning is replayed only inside the current stateless tool loop and is not logged or stored in session history. Geographic and artist constraints remain server-owned during discovery. Source links and local notes come from supplied evidence rather than generated claims. The browser renders plain text through React and does not render model HTML or Markdown.

## Sessions and request protection

A signed, HttpOnly, SameSite cookie identifies a server-owned session. Production cookies use Secure. Trip state has a 30-day sliding inactivity expiry; the local private-file backend survives process restarts and the production Firestore backend coordinates instances. A plan from another session cannot be revised by guessing its identifier. Mutation requests require a custom same-origin header and pass Origin/Fetch Metadata checks. CORS is not enabled.

CSP, restricted response headers, small request bodies, provider URL allowlisting, per-IP request limits, and daily search and planning-attempt ceilings limit the public API surface. Secrets and request bodies are not logged.

A shared transactional key/value store holds signed anonymous sessions and atomic UTC-day quota counters. Production requires Firestore, accessed only by the server through its service identity. Local development uses atomic private JSON files and per-record locks; memory storage is injected only for isolated tests. Planning acquires a short lease, runs provider calls outside transactions, then commits only if its lease and revision still match. Clear trip deletes the record even during a pending operation, preventing late resurrection. Expiry is enforced during access and physical cleanup uses Firestore TTL; local expired records are removed periodically. All payloads are bounded below Firestore’s document limit. Daily app/provider caps persist across restarts; per-IP minute limits remain process-local supplemental protection. Submitted artist and concert-venue IDs missing from a renewed session are revalidated against authoritative Qloo entity types and metadata before planning; client names and coordinates are never trusted. Provider requests reserve usage before each outbound attempt through request-scoped async context; provider quotas remain necessary for spend outside the app. Usage counters retain keyed hashes rather than raw session IDs or IP addresses and expire separately from trip data. Clearing trip data cannot reset global counters. The browser clear flow also resets local drafts and uses a content-free cross-tab signal; generation guards ignore stale asynchronous responses.

## Frontend

Shared color, type, spacing, and border tokens own visual decisions. A deep aubergine accent owns controls, icons, selection, chat accents, and focus rings; placeholders have a separate quieter ink token with a stronger high-contrast preference. Primary form labels and selected values use a consistent 15px medium scale; long prose stays regular, with distinct caption and metadata sizes. Narrow layouts wrap labels instead of shrinking the text. The timeline derives each rail segment, stop node and endpoint marker from one center coordinate, including when endpoint names wrap. Components reuse common form and button primitives. Artist, venue, and starting-point fields share one grouped surface and icon/input row. The default starting point is a true muted placeholder; an empty value submits the venue fallback. Assets are bundled locally, fonts use the system stack, and map directions open externally. Photos use allowlisted public Qloo CDN URLs, are loaded lazily, retain a fixed aspect ratio, show source credit, and fall back to explicit illustrations. Route overview and pending/revision motion respect reduced-motion preferences. The homepage uses thirty overlapping public Qloo photo prints on one composited layer with a restrained blur and slow transform motion. A restrained edge veil and a light glass planning panel keep the inputs in focus while print shapes and colours remain visible. The panel, native pickers, search menus and results share pearl glass surfaces and an aubergine accent with central foreground tokens. Desktop sources are media-gated; mobile renders six softer prints at the same colour strength and loads only their six photo sources. Reduced motion freezes the spread and reduced transparency replaces it with the canvas. The original wordmark sits inside the planning panel. Shared lilac/violet background tokens apply across the homepage, results, sheets, and loading view. Motion and translucency preferences are respected. One typed failure model retains API codes, request status and operation context. Shared recovery cards distinguish field clarification from retryable service failures and preserve form values and chat drafts. Retrying a revision, swap, or restore first reconciles the trusted session against the failed attempt’s revision and conversation snapshot, so a completed operation with a lost response is adopted instead of repeated. Hashed JavaScript and CSS are precompressed with Brotli and gzip at build time. Production bundles do not ship API keys, server provider code, or the sample catalog as a standalone data dump.

## Starting locations

The starting text is interpreted through a bounded structured OpenAI response into a canonical location query and separate city context. The existing Qloo place/address or locality lookup uses the canonical name first, a geographic candidate bias, and at most one contextual fallback. A complete locality miss may use one exact-name public/transit anchor lookup, preserving approximate provider provenance; commercial substitutes, conflicting cities, distant points, ambiguity and outages are not silently accepted; geographic and administrative validation still determines acceptance. The LLM cannot supply coordinates. Locality centers are labeled approximate; duplicate or distant matches have distinct outcomes. A missing match, ambiguity, walking-range limit, missing user detail and provider outage keep separate error codes, so an outage prompts a retry rather than a rewritten address. No additional geocoding service receives the input. Custom starts, the recommendation corridor, every timing estimate, and the first Google Maps leg share the same server-resolved origin. The concert venue remains the final destination.

## Conversational quality

Accepted total-stop bounds are stored separately from matching-kind and fresh-replacement counts. Both suggestion and final validation enforce them; failed updates retain the original plan and memory and explain the unmet count. Broad any-place requests relax earlier soft tastes; deliberate resets may withdraw positive place requirements while submitted time, budget, arrival, origin and exclusions remain independent. Explicit exclusive kinds restrict every selected stop, and category labels never substitute for a specific subtype. Session memory keeps up to 80 shown places and six recent plans, separately from explicitly rejected places and retains bounded place-type tastes and a soft shorter-walk target. Qualitative requests such as “More culture” are retained as preferences: the planner preserves them when compatible, then rebalances older tastes around a later requested kind when they cannot fit together. Explicit must/only/keep requirements remain hard and can only be withdrawn in a relevant user instruction. An explicit “Less walking” update must reduce the current estimate; later requests for different kinds of places can trade a modest amount of walking for a complete feasible outing. The derived show-based outing window, supplied arrival preferences, budget and rejected-place constraints remain hard checks; explicit show-time, exploration-duration, and arrival changes recompute the window together. Requests for fresh alternatives must change actual IDs and use unshown places when feasible; reordering does not qualify. Questions leave the plan and memory unchanged. Chat summaries name verified additions/removals instead of repeating general warnings. Optional local notes carry an exact description excerpt and pass conservative same-place, claim, and evidence checks. Missing evidence leads to omission, with the substantive provider description available as context.

Premium dining uses separate base-type/cuisine, fine-dining and Michelin-discovery facets. Fine-dining evidence comes from vetted Qloo dining tags; a high price alone is insufficient. Explicit high-end tastes exclude known low-tier contradictions and prefer known premium tiers among fine-dining-tagged places without changing the submitted budget. Unknown prices are never labeled expensive. The Resy Michelin Winners collection is discovery and ranking evidence, not verification of current Michelin stars. Accepted alternatives state that limit and disclose missing chosen-day dining hours; an explicit Michelin-only request leaves the current route unchanged when current stars cannot be verified. Fine dining reserves an estimated 90-minute planning allowance, with meal length and reservations left for the user to confirm. Cuisine, food-category checks and all hard itinerary constraints still apply.


The HTTP server keeps a planning connection open while bounded provider calls run. A planning deadline aborts provider requests; a final active-operation check prevents a late result from replacing saved state. Cloud Run should allow 150 seconds so this controlled response can reach the client. Header and request-body timeouts remain finite; a short idle-socket timeout must not interrupt an otherwise valid multi-step request.

## Editing a journey

A one-stop replacement preserves stop count, unaffected positions, the submitted window, and accepted preferences. It checks cached grounded candidates first and uses at most two geographically focused discoveries if necessary; this action does not call the language model. If no valid replacement exists, the original route stays intact. Initial plans prioritize the highest feasible count, up to three stops, before comparing cultural quality.

Up to six earlier plans are stored as trusted session snapshots. Restore accepts only an owned version ID, restores that plan and its preferences, and retains the memory of places already shown. It requires no provider call. The results screen has one chronological photo timeline from the starting point to the concert, with walking legs between stops. A persistent glass dock holds route directions and plan adjustments. Tapping a stop opens its rich place details; chat and earlier versions share one native sheet flow, with labelled Plan details and Earlier plans controls directly above the conversation. Earlier versions display two per page and each can be removed through a session-owned, idempotent endpoint; removal changes neither the active plan nor conversation. The six-version server bound remains in place. Updates preserve stop identity and close only the panel that initiated the operation; drafts survive a visit to earlier plans. Targeted pending states and Undo keep changes understandable without duplicating the route. Visit information uses optional provider phone, neighborhood, website, and listed weekly hours; missing or malformed hours are omitted rather than inferred. Deterministic scheduling rejects visits that conflict with supplied weekly hours, including overnight periods; absent days remain unknown. If final metadata reveals a closure, acceptance retries at most three feasible selections under the same constraints.

The adjustment sheet is a persistent conversation with an anchored composer and an inline view of the current route. Successful chat revisions update the route without closing or remounting the conversation. Drafts and reading position survive sheet navigation, and visual-viewport sizing keeps the composer above a mobile keyboard. Up to 80 display messages remain in the existing server session and are restored on refresh; the model still receives only the last eight messages. Shared material and typography tokens define glass contrast, edge lighting, control depth, and heading weights; base styles load before component styles.

The semantic interpreter dispatches information-only questions to the read-only plan-answers provider: one bounded model call receives current stop evidence, route estimates, optional listed visit facts, and recent conversation. It has no discovery or mutation capability. Mixed explanation-and-change requests stay on the verified revision path.
